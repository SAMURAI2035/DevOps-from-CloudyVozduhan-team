## Процесс настройки 
1) После установки недостающего ПО и оформления структуры репозитория в директории `lab1` я приступила к генерации SSL-сертификата через терминал Git Bash:
```
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout lab1/certs/selfsigned.key \
  -out lab1/certs/selfsigned.crt \
  -subj "//CN=app.local"
```
2) А также выполнила команду для генерации файла `.htpasswd` с помощью Docker:

## Создание nginx.conf
В процессе создания конфига столкнулась с проблемой, из-за которой nginx возвращал ответ со статусом `200` вместо `401` при запросе без заголовка `Authorization`.
Происходило это из-за того, что фаза `Rewrite` выполняется раньше фазы `Access`, поэтому nginx отдавал ответ со статусом `200` и указанным текстом, вообще не доходя до проверки логина и пароля в файле `.htpasswd`. 
Поэтому прямой ответ через `return` я заменила на раздачу статического файла `index.html` через директиву `alias`. (см. lab1/nginx.conf)

## 1. Fast Fuzzing
* Перебор страниц и директорий через `ffuf`: отправление множества HTTP-запросов по словарю и проверка кода ответа.
* Осуществляется для поиска эндпоинтов, по которым nginx может отдать содержимое директории.
1) Скачан [словарь](https://raw.githubusercontent.com/danielmiessler/SecLists/master/Discovery/Web-Content/common.txt) с 4752 эндпоинтами.
2) Скачан `ffuf.exe` (утилита `ffuf` не предустановлена на Git Bash), запущена команда:

![ffuf.png](/assets/lab1/ffuf.png)

3) При запросах к этим эндпоинтам сервер возвращает код HTML-страницы. 
4) `/schedule` и `/tests` должны быть доступны только авторизованным пользователям.
5) `/projects` - только для авторизованных, на самом интерфейсе сайта раздел скрыт, но его можно открыть через строку в браузере:

![projects.png](/assets/lab1/projects.png)

6) `/staff` - при попытке открыть через браузер получаю `403`, при GET-запросе в терминале сервер отдает код HTML-страницы с кодом `200`.
### Вывод: 
Сервер уязвим к некорректной обработке кодов статусов (отдает `200 OK` вместо `401`/`403`) и раскрывает информацию об используемом стекe (Next.js chunks) неавторизованному пользователю.

## 2. Unhandled Host Header / Host Header Injection
* Проверка поведения сервера при запросе с неизвестными или невалидными доменными именами в заголовке `Host`.

### Вывод:
Сервер корректно сбрасывает запросы с некорректным доменным именем в заголовке `Host`, вместо того чтобы отдавать контент чужого виртуального хоста или дефолтную страницу.
## 3. HTTP Verb Tampering
* Проверить конфигурацию прав для HTTP-запросов на закрытом пути.
* Проверяем `HEAD`, `OPTIONS` и `POST` запросы на закрытом пути `/admin`.
